# Concourse v0.2 — Research Checklist

Purpose: things to go learn *before* we design v0.2, so the design conversation
starts informed. Ordered by leverage. The lens throughout (soul.md, and the
"gitless front door" framing): **does this widen the front door for blended-role /
non-dev creators, or does it quietly hand someone a terminal?**

> **Start with Section A.** The Agent SDK / approval shape is load-bearing —
> if it isn't what we hope, it reshapes B, C, and D. Everything else can wait.

CLAUDE.md standing rule still applies: **verify the current SDK/CLI surface against
live docs before writing — don't guess a parameter name.** The docs have moved
before.

---

## A. Load-bearing: Agent SDK + interactive approvals

The v0.1 `CliEngine` is **flag-only** — it can't ask permission mid-turn, which is
why there's no approval modal yet. v0.2's `SdkEngine` is what unlocks it.

- [ ] Current **Agent SDK** package name + `query()` signature (CLAUDE.md flags this as moved).
- [ ] How the SDK surfaces a **permission request** to the host — the `canUseTool` /
      permission-callback shape, and what data it hands you (tool, input, a way to allow/deny).
- [ ] **CLI vs SDK tradeoff:** what you lose leaving the CLI (inherited skills, `.mcp.json`,
      `--resume` semantics, `--bare`). Is a **hybrid** viable — CLI for turns, SDK only for
      permissioning?
- [ ] Does the SDK stream the same event shapes we already normalise, or a different surface?

**Seams already in place:** `CliEngine.capabilities = { permissionCallbacks: false }`;
`normaliseEvent` has a `case '__approval'` that maps a host-internal approval event →
`APPROVAL_NEEDED` (marked `TODO(v0.2, SdkEngine)`); the reducer already turns
`APPROVAL_NEEDED` → `awaiting_approval` ("Needs your OK"). The plumbing waits for a real
permission source.

## B. Multi-agent mesh (the "4 agents on it" panel)

Surface, in a block under the FileTray, that N sub-agents are running + their progress —
Perplexity-style. A front-door **triage** surface.

- [ ] The **`Task`** tool: how sub-agents spawn, `subagent_type`, custom agents
      (`.claude/agents/*.md`).
- [ ] **Verify `parent_tool_use_id`** actually appears on sub-agent events in stream-json
      (we normalise it, but no sub-agent has run under v0.1 to confirm the shape live).
- [ ] **Safety (the real question):** should this audience have `Task` at all, and how to
      scope it? (spec §15: wrap the specific task narrowly, don't hand over the broad tool.)
- [ ] **UX prior art:** screen-record Perplexity's agent spin-up — note what it *shows*
      (count, per-agent label, progress, failures) vs *hides*.

**Seams already in place:** `parentToolUseId` is captured on NARRATION + TOOL events
(`host.mjs` ~L882+); the reducer's `inFlight` map already tracks concurrent tools per id.
**Blocker:** `Task` is NOT in the allowlist (`--allowedTools Read,Glob,Grep,Edit,Write`),
so no sub-agents spawn today.

## C. Memory scoping (sub-agent writes outside the workspace)

Today the driven agent writes memory into the user's real `~/.claude` (it inherits global
settings because we don't pass `--bare`). Display leak is fixed; the write itself isn't.

- [ ] **`autoMemoryDirectory`** — exact setting name + shape in current docs (seen in the
      CLI's "What's new"). Can it point auto-memory into the workspace / `.concourse/`?
- [ ] **`--bare` vs inherited settings** — the full tradeoff (we skip `--bare` on purpose for
      skills + `.mcp.json`, §2.1/§9 — that's the same reason memory leaks out).
- [ ] Decision to make: scope memory in via `autoMemoryDirectory`, disable auto-memory for the
      driven agent, or leave it (display redaction only).

**Seams:** `CliEngine.buildArgs` (where `--bare` / settings flags would go);
`CONCOURSE_CLAUDE_BIN` env already exists for overriding the binary.

---

## D. Permissions & safety model for non-devs

- [ ] Full **permission model**: modes, allow/deny/ask rules, hooks, precedence (we only used
      `--disallowedTools` + `acceptEdits`; there's more, and deny-beats-everything matters).
- [ ] **Skills as narrow capability wrappers** (spec §15): give "export a PDF" without giving
      "run any command."
- [ ] **Workspace sandboxing:** can writes be *hard*-scoped to the workspace, or is it advisory?
      (Ties to C — the memory write escaped the workspace.)

**Seams:** `buildArgs` (`--allowedTools` / `--disallowedTools` / `--permission-mode`);
`WorkspaceFs` already does lexical + symlink path-escape rejection for the *read/download* side.

## E. Product / UX inspiration (blended-role wheelhouse)

- [ ] **Claude Code's new welcome UI** (Recent activity, What's new, rich status line:
      context %, cost, branch, effort). Which translate to a *non-dev* front door, which are
      dev-vocab that must be re-skinned?
- [ ] **Legible cost & progress** — how to show "$1.47 / 35% context" as something a UX lead
      reads without flinching. (We already capture `costUsd` / `durationMs` / `numTurns` on
      `TURN_END`; nothing renders cost yet.)
- [ ] **File attachments** — the driven agent itself flagged this as a v0.2 need; research how
      uploads flow into a workspace-scoped agent (upload → `outputs/` or an `inputs/` dir?).

**Seams:** the outcome box already carries `turn: { durationMs, costUsd, numTurns }`;
the FileTray + `/api/files|file|download` are the file surface to extend for uploads.

---

## F. Reach — how this gets to the UX peeps

- [ ] **Distribution:** v0.1 is single-user loopback (that IS the auth model, §14). How do real
      users run it — packaged app, hosted, per-machine install?
- [ ] **The MCP-App-in-Copilot path** (spec §15): if funded, this host becomes the MCP server
      behind it and `app.html` is discarded — keep the engine/normaliser clean enough that this
      costs a week, not a rewrite. Worth knowing before investing in UI.

## Cross-cutting, already noted

  single-tool-limitation note.)
- **StructureView convergence** — whether Concourse (web-served) complements/replaces the
