## Section A — Agent SDK + interactive approvals

### A1. Package + `query()` signature
- **Package:** `@anthropic-ai/claude-agent-sdk` (npm, TypeScript).
- **Signature:** `query(prompt: string | AsyncIterable<SDKUserMessage>, options?: Options): Query`.
- **Return:** `Query` = `AsyncGenerator<SDKMessage, void>` **plus** mid-turn controls: `.interrupt()`,
  `.setPermissionMode()`, `.setModel()`, `.rewindFiles()`, `.setMaxThinkingTokens()`.
- **Options (key fields):** `model`, `permissionMode`, `mcpServers`, `allowedTools`, `disallowedTools`,
  `canUseTool`, `hooks`, `sessionId` (resume), `forkSession`, `settingSources`.

### A2. The permission source we've been waiting for — `canUseTool`
This is the real source for the `__approval` → `APPROVAL_NEEDED` seam already stubbed in `normaliseEvent`.
```
canUseTool(toolName, input, { signal, toolUseID, requestId, suggestions?, ... })
  => Promise<PermissionResult | null>

PermissionResult =
  | { behavior: "allow"; updatedInput?: Record<string, unknown> }   // optionally edit the input
  | { behavior: "deny";  message: string; interrupt?: boolean }     // block + tell the model
  // return null → defer to the next layer / permission mode
```
- Fires **only for tools not already resolved** by an earlier layer (see A5). It hands the host the
  tool name + input and lets the host allow / deny / **edit-the-input** — which maps cleanly onto our
  `awaiting_approval` state and an approval modal.

### A3. CLI → SDK tradeoff — the SDK effectively supersedes the CLI for programmatic use
Near-full parity; **hybrid is NOT needed**:
- ✅ Skills (`.claude/skills/`), ✅ MCP (`.mcp.json` or `options.mcpServers`), ✅ resume
  (`options.sessionId`), ✅ settings inheritance (`settingSources: ["user","project","local"]` — reads
  CLAUDE.md / `.claude/` rules), ✅ subagents + permissions.
- ❌ **Only known CLI-only gap: "Agent Teams"** (multi-instance coordination) — not in the SDK.
- **Design implication:** v0.2 can go full `SdkEngine` and retire the flag-only `CliEngine` (keep it as
  a fallback if you want, but no functional reason to run both). This unblocks approvals, `setPermissionMode`
  mid-turn, and `.interrupt()` from one surface.

### A4. Event shapes — **same surface, no re-normalization**
The SDK streams the same message union as the CLI's `--output-format stream-json`:
`SDKAssistantMessage` (text + tool_use), `SDKUserMessage` (tool_result), `SDKResultMessage`
(terminal, cost, session id), `SDKStreamEvent` (partial deltas), `SDKSystemMessage`, status markers.
- **Design implication:** our `EventNormaliser` + `StateReducer` carry over almost verbatim. The v0.1
  §5 mapping table stays; `SdkEngine` feeds the same normaliser. That's a big de-risk for the migration.

## The permission model (Section D preview — it's the same surface)

- **Modes:** `default` (unmatched → `canUseTool`), `acceptEdits` (auto-approve Edit/Write/NotebookEdit),
  `plan` (read-only planning, blocks writes), `bypassPermissions` (approve all — trusted CI only),
  `auto` (model classifier), `dontAsk` (deny unmatched, no callback). *(verify the exact set on your version)*
- **Precedence (reported):** PreToolUse hook → **deny rules** → allow rules → ask rules → mode →
  `canUseTool` → PostToolUse. **Deny wins, and deny blocks even under `bypassPermissions`.** A tool
  approved at an earlier layer **skips `canUseTool` entirely.**

## ⚠️ Correction to the earlier antagonist recommendation (#4.1)

I earlier said run the read-only antagonist with `--allowedTools Read,Glob,Grep`. **That is not
sufficient.** Per the SDK docs + a filed issue (anthropics/claude-agent-sdk-typescript #115),
**`allowedTools` does not restrict built-in tools** — Write/Edit/Bash are built-ins and fall through an
allow-list to the permission mode, so an allow-list-only "read-only" agent can still write.

**Hard read-only guarantee = a DENY, not an allow-omission:**
```
disallowedTools: ["Write", "Edit", "NotebookEdit", "Bash"]   // the hard guarantee (deny wins)
permissionMode: "dontAsk"                                     // belt
canUseTool: async () => ({ behavior: "deny", message: "read-only antagonist" })  // suspenders
```
This is the Paper One thesis with teeth: read-only must be an **explicit deny the referee cannot route
past**, not the absence of a grant. (Verify #115's status against your pinned SDK — but designing for
`disallowedTools` is correct regardless, since deny beats allow.)
